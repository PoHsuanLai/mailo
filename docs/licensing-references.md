# Borrowing from open-source mail software: an allow/deny table for mailo

**Status:** research note, not legal advice. Written by the `licensing` researcher agent.
**All licences below were checked against a primary source on 2026-09-22** (project LICENSE/COPYING
file, per-file SPDX header, or package-manager metadata published by the project itself). URLs and
what was actually read are recorded per row. Nothing here is from memory.

**mailo is `MIT OR Apache-2.0`** (`Cargo.toml:14`). That is the constraint
everything else is measured against.

## What I am and am not confident about

**Well-established, low risk of being wrong:**

- Which licence each project carries (verified below).
- That strong copyleft (GPL, AGPL, EUPL) forbids relicensing copied code as MIT/Apache-2.0.
- That MPL-2.0 is file-level and that a pasted function makes *that file* MPL.
- That copyright protects expression, not facts, ideas or procedures — this is statute in the US
  (17 U.S.C. §102(b)) and in the EU (Software Directive 2009/24/EC Art. 1(2)).

**Genuinely uncertain, would need a lawyer if it ever mattered:**

- Exactly where "learned a fact" becomes "close paraphrase of a protected algorithm". There is no
  bright line; courts apply abstraction-filtration-comparison (*Computer Associates v. Altai*) case
  by case. The rule in §1 below is a working heuristic, not a safe harbour.
- Whether a *very* short copied fragment (a constant table, a five-line state transition) is
  de minimis. Probably, usually, but "probably" is doing real work in that sentence.
- Anything about patents. None of this touches patents.
- Non-US jurisdictions beyond the EU directive.

I am not a lawyer. Treat this as an engineering hygiene document that happens to be about law.

### Tooling caveat worth writing down

GitHub's licence API returns exactly **one** SPDX id and cannot express dual licensing. For every
dual-licensed Rust crate above it reported only `Apache-2.0`. It also returned *nothing* for
`mail-parser`/`mail-builder` (REUSE layout) and `NOASSERTION` for Dovecot, Cyrus, notmuch,
OfflineIMAP and MailCore2. **Do not let an automated licence scan be the last word.** The
authoritative sources, in order: per-file SPDX header → `Cargo.toml`/package metadata →
`LICENSE`/`COPYING` → scanner.

## 1. Where the line is between "learning a fact" and "creating a derivative work"

### The legal frame, briefly

Copyright protects *expression*, not ideas, procedures, processes, systems or methods of
operation. That is the literal text of 17 U.S.C. §102(b), and the EU Software Directive
(2009/24/EC Art. 1(2)) says the same for "ideas and principles which underlie any element of a
computer program, including those which underlie its interfaces". The CJEU confirmed in *SAS
Institute v. World Programming* (C-406/10) that functionality, programming languages and data
file formats are not protected as such.

Two doctrines do most of the work in our situation:

- **Merger.** When there is essentially only one sensible way to express an idea, the expression
  merges with the idea and is not protected. Most protocol-handling code is close to this.
- **Scènes à faire.** Elements dictated by external constraints — here, the RFC and the server's
  actual behaviour — are not protected.

One correction to a commonly-repeated claim: *Google v. Oracle* (2021) did **not** hold that APIs
are uncopyrightable. The Court assumed copyrightability for argument's sake and decided the case
on **fair use**. Don't build a policy on "APIs aren't copyrightable"; build it on §102(b) and
merger, which are firmer ground.

### The practical rule

**The note-and-close rule.** Reduce what you learned to a sentence about observable behaviour.
Close the source. Write the code from the sentence.

Concretely, three steps:

1. **Read.** Open the foreign source. Understand the *why*.
2. **Write the sentence.** In your own words, in a scratch note or an issue, state the fact:
   *"Gmail returns `* CAPABILITY` again after `LOGIN` and the post-auth list differs from the
   pre-auth list, so a client must re-read capabilities after authenticating."*
   *"Exchange sends `BODYSTRUCTURE` with a `NIL` where RFC 9051 requires a string, for
   `message/rfc822` parts with no envelope."*
3. **Close the file, then implement.** If you cannot write your implementation without the
   source open, you are copying, not learning.

**The one-sentence test:** *if what you took fits in a sentence about what the server does, it is a
fact and it is yours. If you would need the source visible to reproduce it, it is expression and
it is theirs.*

### The complication the one-sentence test doesn't cover

Some things are neither a bare fact nor a verbatim copy: a **non-obvious algorithm** — a
non-trivial UID-set diffing strategy, a specific back-off-and-resync state machine, an ordering of
operations that makes an interrupted sync recoverable. The *idea* is unprotected; a close
paraphrase of the *implementation* can still be infringing (structure, sequence and organisation
can be protected — *Whelan*, refined by *Altai*'s abstraction-filtration-comparison).

For that category, escalate:

- **Describe it at a level above the code** — a paragraph of prose or a state diagram, not a
  transliteration. If your note has the same variable names, it is not a note, it is a transcript.
- **Let it go cold.** Implement it the next day, or after another task. Independent re-derivation
  from a description is the thing that makes the result yours.
- **Split the roles** for anything high-stakes taken from a GPL codebase: one person reads and
  writes a behavioural spec; a different person implements from the spec without reading the
  source. This is clean-room-lite. It is overkill for "the server re-issues CAPABILITY"; it is
  proportionate for "how does mbsync survive a torn sync". Honestly, if a problem is that valuable
  and only a GPL project has solved it, the cheaper answer is to find a permissive implementation
  or to work it out from the RFC.

### Red flags — if any of these are true, you copied

- Identifier names match, or match after mechanical translation (`fMsgUid` → `msg_uid`).
- Comments survive, even reworded.
- Branch order and early-return structure match.
- Magic constants match beyond what the protocol dictates (a 30-second timeout is not a fact about
  IMAP; `\r\n.\r\n` is).
- Error message strings match.
- The same bug is present.
- You could not explain any line without re-opening the source.

### Green — these are facts and are free

- Wire syntax, grammar, ABNF (and the RFC's own ABNF is BSD-licensed — copy it, cite it).
- Capability names, command names, response codes, flag names, header field names.
- "Server X violates the spec in way Y." "Server X needs workaround Z." "Ordering A before B
  avoids failure C."
- Numeric limits a server actually enforces.
- Public API shapes of a *library you depend on* (you need them to call it).

## 2. MPL-2.0 (Thunderbird desktop, Delta Chat core): what "file-level copyleft" concretely means

MPL-2.0 is often described as "the reasonable copyleft", which is true and which is exactly why
people get careless with it. The unit of copyleft is **the file**.

### What happens if you paste an MPL function into `crates/mail-proto/src/imap/fetch.rs`

1. **That file becomes Covered Software.** MPL §1.4 defines Covered Software as the Source Code
   Form to which the initial Contributor attached the notice, *plus* Modifications. §1.10 defines a
   Modification to include "any file in Source Code Form that results from an addition to,
   deletion from, or modification of the contents of Covered Software". Our file now contains their
   code; it is covered.

2. **That file must be distributed under MPL-2.0.** §3.1: source must be made available under
   MPL terms to anyone who receives the executable. Not "on request", not "eventually" — as a
   condition of distributing.

3. **You may not strip the header.** §3.4 requires the licence notices to be preserved. Deleting
   the "This Source Code Form is subject to the terms of the Mozilla Public License, v. 2.0"
   comment is itself a licence violation, and it is the *first* thing a careless paste does.

4. **You cannot relicense that file as MIT or Apache-2.0.** So our repo-level claim
   `license = "MIT OR Apache-2.0"` becomes **false**. Cargo has no per-file licence field, so the
   honest SPDX expression for the crate becomes something like
   `(MIT OR Apache-2.0) AND MPL-2.0` — which is a different, and worse, promise than the one we
   are making today.

5. **Downstream consequences.** A user who took mailo under MIT because they wanted no
   file-availability obligation now has one for that file. A user who took it under Apache-2.0 for
   the patent grant doesn't get that grant on that file. Anyone vendoring mailo into a proprietary
   product now has an MPL source-availability duty they did not sign up for. None of these are
   catastrophes; all of them are surprises, and surprises are what licensing hygiene exists to
   prevent.

### What MPL-2.0 does *not* do

It is **not** viral across files. §3.3 explicitly permits distributing a "Larger Work" under other
terms provided the MPL files keep their terms. You may depend on, link against, and ship alongside
MPL code freely — which is why Delta Chat core and Thunderbird are tier **R** and not tier **D**.
The binary is fine. The file is the problem.

### The practical consequence for us

There is a legitimate escape hatch: **quarantine**. Put the borrowed code in its own file,
`crates/mail-proto/src/imap/mpl/bodystructure_quirks.rs`, with the MPL header intact, and touch
nothing else. That is lawful and honest.

**My recommendation is to not do it anyway**, for engineering rather than legal reasons: it
permanently complicates the crate's licence expression, it means `cargo deny` / SBOM output that
needs explaining forever, it means downstream packagers ask questions, and it costs more in
ongoing friction than re-deriving the behaviour from a trace costs once. For a mail client the
payoff is especially poor, because what Thunderbird knows that we don't is almost always a *fact
about a server*, and facts are free (§1).

**The one rule to remember:** reading Thunderbird is fine and encouraged. `nsImapProtocol.cpp` and
`nsImapGenericParser.cpp` encode twenty-five years of real-world IMAP pathology. Pasting from it is
a licence change to one of our files. Those two sentences are the whole of it.

## 3. GPL-2.0 vs GPL-3.0: is there a meaningful difference for us?

**For the direction we care about — their code coming into mailo — no. None whatsoever.** Both
forbid relicensing under MIT/Apache-2.0. isync, OfflineIMAP, fetchmail, getmail, NeoMutt (GPLv2
family) and meli, Roundcube, Mailspring, notmuch, msmtp (GPLv3 family) are all equally tier D. Do
not spend time on this distinction when deciding whether to copy; the answer is no either way.

Four places where the difference *is* real, none of them load-bearing for us:

1. **Apache-2.0 compatibility, in the other direction.** GPL-2.0 is incompatible with Apache-2.0
   (the FSF's long-standing position, on the patent-termination and indemnity terms). GPL-3.0 is
   compatible — Apache-2.0 code can be taken into a GPLv3 project. **This is why our dual licence
   is the right call:** if a GPLv2-only project such as getmail6 ever wanted to take mailo code,
   they could take the **MIT** half; the Apache half alone would block them. Worth knowing; it
   costs us nothing and we already have it.

2. **"or-later" matters more than the version number.** `GPL-2.0-or-later` (isync, OfflineIMAP,
   fetchmail, NeoMutt) lets a downstream user pick GPLv3, which restores Apache compatibility.
   `GPL-2.0-only` (**getmail6**) does not, and is the most isolated licence in this document —
   GPLv2-only code cannot even be combined with GPLv3 code. If anyone is ever tempted to argue
   "the exception in project X might let us...", the `-only` vs `-or-later` suffix is the first
   thing to check, not the last.

3. **GPL-3.0 adds** anti-tivoization (installation information for User Products), an explicit
   patent grant with retaliation terms, and a cure period for violations. Relevant if we ever
   *shipped* GPL code. We do not intend to.

4. **AGPL-3.0 is the one that is genuinely different in kind**, and it is worth separating from
   both: it extends the source-offer obligation to **network interaction**, not just distribution.
   For a *client* like mailo the network trigger rarely fires — but the copying prohibition is the
   same, and the blast radius if anyone ever ran a mailo-derived service is larger. Stalwart
   `sieve`, Stalwart's servers and Nextcloud Mail are the AGPL entries here. Treat them as the
   sharpest edge: correct to read, worst to reflexively paste.

**Summary for the team:** stop distinguishing GPLv2 from GPLv3. Distinguish **permissive / weak
(MPL, LGPL) / strong (GPL, AGPL, EUPL)**. Three buckets, not six.

## 4. Provenance hygiene: how to record this so it doesn't become folklore

The failure mode is not a lawsuit. It is that in eighteen months nobody remembers why
`fetch.rs:214` special-cases a `NIL` body-structure, someone "cleans it up", and a Gmail account
breaks. The provenance record and the correctness record are the same artifact. Design for that.

### 4.1 Cite the observed behaviour, not the client

**Bad:**
```rust
// Taken from mbsync driver.c:412 -- see how isync handles UIDVALIDITY changes.
```
Three separate problems: it is a pointer to GPLv2 code sitting in an `MIT OR Apache-2.0` crate,
which reads to any auditor as an admission of copying; it is not a licence grant, so it fixes
nothing if we *did* copy; and it does not actually tell the next reader what the server does,
which is the information they need.

**Good:**
```rust
// Dovecot 2.3 bumps UIDVALIDITY when a mailbox is renamed and back, so a client that
// trusts a cached UID set after a rename resurrects deleted mail. RFC 9051 s2.3.1.1
// permits the bump; it does not require the client to be warned.
// Trace: tests/traces/imap/uidvalidity_bump_after_rename.trace
```
This is better on every axis. It states the fact, it cites the spec, and it points at a test that
*proves* the fact in our own repository.

**The distinction that matters, stated plainly:** this is about *where the information lives*, not
about concealment. If you genuinely **copied** code, you must attribute it properly and comply with
its licence — stripping an attribution to make a provenance problem invisible is fraud, not
hygiene. Rule 4.1 applies to the case where you learned a *fact*; rule 4.3 applies to the case
where you took *code*. Know which one you are in before you write the comment.

### 4.2 Our own traces are the evidence — and we already have the machinery

`crates/mail-proto/tests/traces/FORMAT.md` already establishes that every protocol test is a
transcript and that the format is a frozen interface. `spike/out/imap.trace` is already a real
Gmail session with credentials redacted. That infrastructure is the provenance system; it just
needs one convention added.

**Proposal: a standard provenance header on every trace.** The format already supports `#`
comments and the FORMAT.md example already uses them informally ("NTU POP3, recorded 2026-09-22,
addresses scrubbed"). Make it structured and required:

```
# server:    Dovecot 2.3.21 (greeting: "* OK [CAPABILITY ...] Dovecot ready.")
# recorded:  2026-09-22
# account:   personal test account, scrubbed per FORMAT.md
# quirk:     UIDVALIDITY increments on rename-and-rename-back
# spec:      RFC 9051 s2.3.1.1
# source:    observed directly. Not derived from any other client's source.
```

That last line is the whole point. It is a positive, dated, in-repo statement that this knowledge
came from a socket and not from someone's GPL source file. It is far stronger evidence than a
comment saying where we *didn't* get something, and it costs one line.

Where a quirk was learned from reading — as opposed to observed — say that instead, honestly:
`# source: behaviour described in <permissive project>; independently reproduced against a live server 2026-09-22.`
Reproducing it against a live server is what converts secondhand knowledge into a fact we own.

Two supporting rules, both already implied by FORMAT.md and worth making explicit:

- **Scrub, keep shape.** FORMAT.md already says this. Extend it: redact credentials, addresses,
  subjects, message-ids and hostnames; preserve header order, folder names, UID magnitudes and
  encodings. A scrubbed trace that lost its quirk lost its value.
- **A quirk without a trace is a rumour.** If someone proposes a workaround and cannot produce a
  transcript, that is the review comment. This is also a correctness rule, not only a licensing one.

### 4.3 When an approach came from a permissively-licensed project, say so — properly

For tier-A sources this is not a risk to be managed, it is a **condition of the licence** and a
courtesy that costs nothing.

- **If you copied more than a trivial amount**, keep the upstream copyright line, add the upstream
  licence text to a `licenses/` or `THIRD-PARTY-NOTICES.md` in the repo root, and — for Apache-2.0
  — comply with §4(b) (**mark modified files as changed**) and §4(d) (**propagate the NOTICE**).
  K-9/Thunderbird-Android and Apache James both carry NOTICE obligations.
- **If you only took the idea**, one comment line:
  ```rust
  // Approach follows imap-codec (MIT OR Apache-2.0): parse into a borrowed AST first,
  // validate in a second pass, so a malformed literal can't poison the reader state.
  ```
  Naming a permissive project is safe, useful, and generous. Naming a copyleft project in the same
  breath is the thing to avoid (§4.1).
- **A short header block for ported files:**
  ```rust
  //! Modified UTF-7 codec.
  //!
  //! Ported from utf7-imap (MIT, (c) Ilya Medvedev), with the error type replaced and
  //! the surrogate-pair handling rewritten. See licenses/utf7-imap-MIT.txt.
  ```

### 4.4 Make it mechanical, not cultural

Folklore is what happens when a rule lives only in people's heads.

- **Land this file in the repo**, as `docs/licensing-references.md` or an ADR. It has SPDX + URL +
  date per project; a new contributor should not have to re-derive it. Re-verify annually or on any
  major version bump — licences change, and two entries here (meli, io-oauth) have *already*
  changed.
- **Add `cargo deny` with a `[licenses]` allow-list** to CI. `deny.toml` does not currently exist in
  the repo. An explicit allow-list of `MIT`, `Apache-2.0`, `BSD-2/3-Clause`, `ISC`, `0BSD`,
  `Unicode-3.0` turns "we accidentally pulled in a GPL crate" from a discovery into a red build.
- **Add a `Ref:` trailer convention to commit messages** — pointing at an RFC section or a trace
  fixture, never at foreign source. This repo's commit style is already narrative
  ("Phase 0: run the spike, and fix what it disproved"); a trailer fits.
- **The strongest single rule: when two projects document the same behaviour, read the permissive
  one.** imap-codec and meli both know what Gmail does with `X-GM-LABELS`. Read imap-codec. This
  costs nothing and eliminates the entire category of risk before it arises.

### 4.5 The AI-delegation rule — specific to how this repo works

This project delegates implementation volume to Grok and gates it through Claude review
(`memory/MEMORY.md`). That makes one rule non-optional:

**Never put GPL/AGPL/MPL source into a model's context and then ask it to write the equivalent
code.** A model that has just read `nsImapProtocol.cpp` and is asked to "implement this in Rust" is
not applying the note-and-close rule — it is doing the *opposite* of it, producing exactly the
close paraphrase §1 warns about, at speed and at volume, with no human who could later testify to
independent derivation.

What to put in the prompt instead: **the trace file and the RFC section.** Both are things we own
or that are BSD-licensed. That is not a workaround; it is the same discipline as §1, applied to a
faster typist.

Note also that meli explicitly refuses LLM-generated contributions. We are not contributing to
meli, so it does not bind us — but it is a reminder that norms in this ecosystem are stricter than
the licences, and being seen to have fed a copyleft mail client into a code generator would cost us
goodwill we cannot buy back.

## Appendix: verification method

Every row was checked on **2026-09-22** by fetching one or more of:
